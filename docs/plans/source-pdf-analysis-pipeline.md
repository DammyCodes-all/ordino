# PDF Analysis Pipeline Plan

## Goal

Add an Ordino workflow for analyzing any PDF artifact:

- uploaded PDFs from the user
- PDFs generated by Ordino from the canonical `DocumentState`

The same analysis, highlighting, simplification, translation, narration, and annotated export flow should work for both sources.

1. Ingest a user PDF locally.
2. Convert each page into a page image.
3. Extract raw text and positional text spans with `unpdf`.
4. Send page image + extracted text context to Gemma through the existing server-side Google AI route pattern.
5. Identify important content such as deadlines, money, signatures, obligations, risks, rights, and required actions.
6. Generate plain-language explanations and translations in the user's selected language.
7. Render highlights back onto the PDF viewer and exported annotated PDF.
8. Generate narration text for text-to-speech.

This workflow should build beside the current generated-document workflow, but generated Ordino PDFs should be first-class inputs. Do not force uploaded source PDFs into the existing canonical `DocumentState` node model. For generated Ordino PDFs, preserve the link back to `DocumentState` as optional context.

## Product Scope

### In scope

- Upload a PDF.
- Analyze an Ordino-generated PDF after `PdfPort.render`.
- Extract page text and positional text spans with `unpdf`.
- Render page images for model vision input and UI preview.
- Analyze pages with Gemma using both image and extracted text.
- For generated PDFs, include document metadata, outline, and node text as additional model context.
- Identify important clauses or fields contextually, not through regex-only rules.
- Explain each highlight in simple language.
- Translate each explanation into the selected language.
- Show highlights in a page viewer.
- Show a side panel with source text, explanation, translation, category, and confidence.
- Generate narration segments from the simplified or translated explanations.
- Export an annotated PDF with highlights.

### Out of scope for first implementation

- OCR for scanned/image-only PDFs.
- Perfect coordinate recovery for pages without embedded text.
- Legal or financial advice claims.
- Direct editing of the original PDF content.
- Persisting uploaded PDF blobs unless explicitly approved later.
- Cloud TTS unless browser speech is insufficient.

### Input Adapter Pattern

The analysis pipeline should not care whether the PDF came from upload or from Ordino rendering. Use adapters that produce the same canonical analysis input:

```ts
type AnalyzablePdfOrigin = "uploaded_pdf" | "ordino_generated_pdf";

interface AnalyzablePdfInput {
  analysisDocumentId: AnalysisDocumentId;
  origin: AnalyzablePdfOrigin;
  fileName: string;
  pdfBlob: Blob;
  generatedDocumentContext: GeneratedDocumentContext | null;
}

interface GeneratedDocumentContext {
  documentId: DocumentId;
  documentVersion: number;
  title: string;
  documentType: string;
  audience: string;
  outline: DocumentOutline;
  nodeTextDigest: GeneratedNodeTextDigest[];
}

interface GeneratedNodeTextDigest {
  nodeId: NodeId;
  type: string;
  text: string;
}
```

Adapters:

- uploaded PDF adapter: wraps the uploaded `File` as an `AnalyzablePdfInput` with `generatedDocumentContext: null`
- generated PDF adapter: takes `DocumentState` + `InternalRenderResult.pdfBlob` and includes document metadata, outline, and node text digest

This keeps one analysis pipeline while allowing generated PDFs to benefit from source structure that uploaded PDFs do not have.

## Dependency Plan

Add `unpdf` as the source PDF extraction layer.

Use `unpdf` for:

- loading PDF files
- extracting page text
- accessing page-level PDF.js text content for positional spans
- rendering pages to images where practical

Keep `pdfjs-dist` available for the existing generated-PDF validation/rasterization work unless we deliberately consolidate later.

Potential later dependency:

- `pdf-lib` for annotated export if drawing overlays onto the original PDF is awkward with the existing stack.

Dependency changes should be coordinated through the repo owner for `package.json` and `pnpm-lock.yaml`.

### Analysis Document

```ts
interface AnalysisDocument {
  schemaVersion: 1;
  analysisDocumentId: AnalysisDocumentId;
  origin: "uploaded_pdf" | "ordino_generated_pdf";
  fileName: string;
  pageCount: number;
  pages: AnalysisPage[];
  generatedDocumentContext: GeneratedDocumentContext | null;
  createdAt: string;
}

interface AnalysisPage {
  pageNumber: number;
  widthPx: number;
  heightPx: number;
  image: AnalysisPageImage;
  rawText: string;
  textSpans: PdfTextSpan[];
}

interface AnalysisPageImage {
  mimeType: "image/png";
  dataUrl: string;
  widthPx: number;
  heightPx: number;
}

interface PdfTextSpan {
  id: PdfTextSpanId;
  pageNumber: number;
  text: string;
  x: number;
  y: number;
  width: number;
  height: number;
  fontName: string | null;
  fontSize: number | null;
}
```

Coordinates should be normalized to the rendered page image coordinate system used by the UI. That avoids translating between PDF points, viewport pixels, and CSS pixels in several places.

### Analysis Request

```ts
interface PdfAnalysisRequest {
  analysisDocumentId: AnalysisDocumentId;
  origin: "uploaded_pdf" | "ordino_generated_pdf";
  targetLanguage: string;
  pages: PdfAnalysisPageInput[];
  generatedDocumentContext: GeneratedDocumentContext | null;
  userGoal: string | null;
}

interface PdfAnalysisPageInput {
  pageNumber: number;
  imageDataUrl: string;
  rawText: string;
  textSpanDigest: PdfTextSpanDigest[];
}

interface PdfTextSpanDigest {
  id: PdfTextSpanId;
  text: string;
}
```

Do not send every positional field to Gemma unless needed. The model mostly needs the text and stable span IDs. Local code owns the coordinates. For generated PDFs, send the generated document context as a compact structural aid, not as a replacement for visual/page analysis.

### Highlights

```ts
type HighlightKind =
  | "deadline"
  | "money"
  | "signature"
  | "obligation"
  | "risk"
  | "right"
  | "termination"
  | "required_action"
  | "other";

interface DocumentHighlight {
  id: HighlightId;
  analysisDocumentId: AnalysisDocumentId;
  pageNumber: number;
  kind: HighlightKind;
  severity: "info" | "important" | "critical";
  sourceText: string;
  matchedSpanIds: PdfTextSpanId[];
  relatedNodeIds: NodeId[];
  boundingBoxes: HighlightBoundingBox[];
  plainLanguageText: string;
  translatedText: string;
  targetLanguage: string;
  reason: string;
  confidence: number;
}

interface HighlightBoundingBox {
  pageNumber: number;
  x: number;
  y: number;
  width: number;
  height: number;
}
```

Gemma should return source text and candidate span IDs when available. For generated PDFs, it may also return candidate node IDs from the supplied outline/text digest. The application validates those IDs, generates final highlight IDs, and computes final bounding boxes.

### Narration

```ts
interface NarrationSegment {
  id: NarrationSegmentId;
  highlightId: HighlightId | null;
  pageNumber: number | null;
  text: string;
  language: string;
  order: number;
}
```

For MVP, narration can use browser `speechSynthesis`. The contract should not assume a specific TTS provider.

## Data Flow

### 1. Ingest

Input:

- uploaded PDF `File`, or
- Ordino `DocumentState` plus matching `InternalRenderResult.pdfBlob`
- target language
- optional user goal

Local processing:

1. Convert the input into `AnalyzablePdfInput`.
2. Load the PDF blob with `unpdf`.
2. Determine page count.
3. For each page:
   - render a page image
   - extract raw text
   - extract text items
   - convert text items into normalized `PdfTextSpan[]`
4. Attach generated document context when the PDF origin is `ordino_generated_pdf`.
5. Return an `AnalysisDocument`.

Output:

```ts
AnalysisDocument
```

Failure cases:

- unsupported file type
- corrupt PDF
- encrypted PDF
- empty PDF
- page render failure
- text extraction failure

Text extraction failure should not necessarily block analysis if page images exist, but MVP can mark those pages as visual-only and skip exact overlays.

### 2. Analyze

Input to model:

- page image
- raw page text
- compact span digest
- generated document context when available
- target language
- user goal
- strict JSON schema instructions

Gemma responsibilities:

- understand the page in context
- identify meaningful highlights
- classify each highlight
- explain why it matters
- simplify the meaning
- translate the explanation
- produce narration-ready wording

Gemma should not be trusted to:

- create final application IDs
- compute final coordinates
- make legal or financial claims as advice
- mutate persisted app state

For generated PDFs, Gemma should be told that `generatedDocumentContext` is a structural hint from Ordino's source document. The rendered page image and extracted PDF text remain the source of truth for what appears in the PDF.

### 3. Normalize

Local code receives raw model output and:

1. Validates with Zod.
2. Runs one structured repair request if validation fails.
3. Discards invalid page numbers.
4. Discards unknown span IDs.
5. Discards unknown generated node IDs.
5. Matches `sourceText` against `PdfTextSpan[]` when span IDs are missing.
6. Computes bounding boxes from matched spans.
7. Generates final app IDs.
8. Produces `DocumentHighlight[]`.

Matching should prefer:

1. exact span ID match from model output
2. exact contiguous source text match
3. normalized fuzzy text match
4. no overlay, side-panel only

### 4. Transform

The first model call should produce both simplification and translation:

```text
source text -> plain-language explanation -> translated explanation
```

Avoid a separate word-for-word translation pass unless quality testing shows it is needed.

### 5. Output

UI output:

- PDF page image viewer
- highlight overlays
- side panel
- summary/action list
- narration controls
- export button
- for generated PDFs, optional action to continue editing the underlying Ordino document after viewing analysis

Export output:

- annotated PDF with highlights
- optional appendix with translated explanations

Narration output:

- ordered `NarrationSegment[]`
- browser TTS playback

## Model Route Plan

Add a new same-origin route:

```text
POST /api/ai/pdf-analysis/analyze
```

Rules:

- The browser never calls Google directly.
- `GOOGLE_GENERATIVE_AI_API_KEY` stays server-only.
- Validate request body size and shape at the route boundary.
- Do not log prompts, image data URLs, PDF text, provider payloads, or secrets.
- Return structured `AppResult`.
- Convert provider failures to shared error codes.
- Use the same structured-output repair policy as the generated-document agent.

Suggested batching:

- Analyze 1-3 pages per model request for MVP.
- Merge page outputs locally.
- Add a final document-level synthesis pass after page analysis.

Document-level synthesis should produce:

- top deadlines
- top required actions
- total monetary obligations
- signature requirements
- critical risks
- concise summary in selected language

## Prompt Strategy

Prompt principles:

- Tell Gemma it receives both visual page context and extracted text.
- When available, tell Gemma it also receives Ordino's generated document metadata, outline, and node text digest.
- Require exact source excerpts.
- Ask for candidate span IDs when possible.
- Ask for candidate generated node IDs only when the PDF originated from an Ordino document.
- Ask it to identify meaning, not just keywords.
- Require plain-language explanations.
- Require translations in the selected language.
- Require uncertainty when the source is ambiguous.
- Prohibit advice claims.
- Require JSON only.

The model output should include:

```ts
interface RawHighlight {
  pageNumber: number;
  kind: HighlightKind;
  severity: "info" | "important" | "critical";
  sourceText: string;
  candidateSpanIds: string[];
  candidateNodeIds: string[];
  plainLanguageText: string;
  translatedText: string;
  narrationText: string;
  reason: string;
  confidence: number;
}
```

Uploaded PDF workflow:

4. App ingests PDF locally.
5. App sends page analysis requests through same-origin route.
6. App shows progressive status.

Generated PDF workflow:

1. User generates or updates a document through the existing Ordino workflow.
2. `AgentPort.runTurn` returns a final `InternalRenderResult`.
3. User chooses Analyze PDF.
4. App builds an `AnalyzablePdfInput` from the current `DocumentState` and `finalRender.pdfBlob`.
5. User chooses target language and acknowledges cloud processing disclosure if needed.
6. App runs the same PDF analysis pipeline.
7. App renders highlights over the generated PDF preview.
8. User can play narration, export annotated PDF, or return to chat editing.

Cloud disclosure must clearly state:

- page images and extracted text are sent to Google AI Studio for analysis
- document processing and persistence are local where applicable
- AI analysis requires internet access
- the API key is never entered or sent by the browser

## Persistence Plan

Persist:

- analysis document metadata
- origin: uploaded or Ordino-generated
- generated document reference when applicable
- selected target language
- extracted raw text
- text spans
- model analysis result
- highlights
- narration segments

Do not persist for MVP:

- uploaded PDF blob
- rendered page image data URLs
- exported annotated PDF blob
- object URLs
- provider payloads

On reload:

- restore analysis JSON
- ask user to re-upload the source PDF if an uploaded PDF's page images or export are needed
- for generated PDFs, regenerate the PDF from current `DocumentState` when the stored `documentVersion` still matches
- optionally regenerate page images if the original file is available in memory only

If we later choose to persist uploaded PDFs, make that an explicit product/security decision.

## Export Plan

MVP export should produce an annotated PDF.

Preferred implementation:

1. Keep the source PDF blob in memory during the session.
2. Draw translucent highlight rectangles using normalized coordinates.
3. Save as a new PDF blob.
4. Use a sanitized filename like:

```text
original-name-annotated.pdf
```

For generated PDFs, derive the filename from `DocumentMeta.title`, for example:

```text
document-title-analysis.pdf
```

If `unpdf` does not support writing annotations directly, use `pdf-lib` for this part.

Optional appendix:

- page number
- source text
- explanation
- translation
- category/severity

## TTS Plan

MVP:

- use browser `speechSynthesis`
- play `NarrationSegment[]` in order
- allow play/pause/stop
- allow reading one highlight or the full document summary

Later:

- add server-side cloud TTS if we need better voices, generated audio files, or exportable narration.

## Error Handling

Use typed app errors for:

- invalid PDF
- encrypted PDF
- extraction failed
- page render failed
- model unavailable
- model output invalid
- rate limited
- internet required
- unsupported language
- export failed
- narration unavailable

Do not lose completed analysis if a later page fails. Return partial results with clear failed-page status where possible.

## Security and Privacy

- Never expose `GOOGLE_GENERATIVE_AI_API_KEY` to the browser.
- Never use a `NEXT_PUBLIC_` API key.
- Never log uploaded PDF text, page images, prompts, provider responses, or TTS text.
- Make cloud transfer explicit before analysis.
- Avoid persisting uploaded PDFs in MVP.
- Add a user-facing note that explanations are informational and not legal or financial advice.

## MVP Acceptance Criteria

- User can upload a text-based PDF.
- User can analyze an Ordino-generated PDF from the current final render.
- App extracts text and positional spans with `unpdf`.
- App renders page images.
- User can select a target language.
- User acknowledges cloud transfer before analysis.
- Gemma receives page image + extracted text through a server route.
- App shows contextual highlights for deadlines, money, signatures, obligations, and risks.

- App still shows side-panel explanations when overlay matching fails.
- Browser TTS can read explanations.
- User can export an annotated PDF.

## Key Technical Risk

The biggest risk is coordinate quality. `unpdf`/PDF.js text items can provide positional data, but PDF text layout is not always clean. The plan should treat exact overlay placement as best effort and keep the side panel as the reliable fallback.

## Recommended First Build Slice

Build the smallest end-to-end vertical slice:

1. Generate a simple Ordino PDF from the existing document flow.
2. Adapt its `InternalRenderResult.pdfBlob` into `AnalyzablePdfInput`.
3. Extract page 1 image, raw text, and spans.
4. Send page 1 to the analysis route with a fake model response first.
5. Normalize one highlight.
6. Draw one overlay on the generated PDF preview.
7. Show one explanation in the side panel.
8. Speak one narration segment.

Then repeat the same flow with one uploaded text-based PDF to verify that both origins use the same pipeline.

Once that works, expand to multi-page batching and real Gemma output.
